The problem

Everyone ships "done."
Nobody ships proof.

"It works" is the most expensive sentence in software. Three failure modes the standard kills on contact:

FAIL_01

The vibes demo

One cherry-picked run, one lucky seed, declared victory. Single runs prove nothing — variance hides in the noise floor.

FAIL_02

The gaming procedure

Optimize the scoreboard, not the outcome. Goodhart's law ships to production and the real metric never moves.

FAIL_03

The strawman baseline

"We beat the naive approach." Against a weak baseline, anything looks like genius. A fair fight needs a tuned opponent.

The standard

Six gates. All must pass.
One failure = no commit.

The judge() runs every candidate through all six — automatically, before anything is allowed to be called done.

GATE 01 — COMMIT

Frozen before the evidence exists

Both procedures are fingerprinted and committed before the sealed test seed is drawn. No post-hoc tuning, no moving goalposts.

GATE 02 — PARITY

Same instances, same budget

Candidate and baseline see identical instances with identical compute budgets. random.Random(1) for both. No resource cheating.

GATE 03 — PLACEBO

Gain must come from the instance

Scored against mismatched hidden truths. If the gain survives a placebo, it's just the prior — not skill.

GATE 04 — PAIRED WIN

Statistically significant, effect-sized

Bootstrap lower confidence bound on the paired difference must clear zero. Bonferroni-corrected across slices. Luck doesn't pass.

GATE 05 — GOODHART

Truth gain must not lag proxy gain

If the optimizable proxy improves faster than the sealed truth signal, the procedure is gaming its own scoreboard. Flagged, not shipped.

GATE 06 — COST

No winning by burning compute

Candidate runtime is held against a slack multiple of the baseline. Victory by brute force is a cost failure, not a win.

The algorithm — the patterns that make gold

We didn't invent these.
We enforce them.

Every gate in GOLD is a named, published pattern from statistics and AI evaluation. The standard's job is not novelty — it's making sure none of them get skipped under deadline pressure. Sources are linked; follow them.

GATE 05↗

Goodhart's Law

When a measure becomes a target, it ceases to be a good measure. GOLD checks that gain on the optimizable proxy never outruns gain on the sealed truth signal.

wikipedia.org/wiki/Goodhart's_law
GATE 03 + 05↗

Specification gaming

DeepMind's catalogue of agents achieving the letter of the objective while violating its spirit. The placebo gate is designed to catch exactly this: gain against a mismatched truth is prior, not skill.

deepmind.google — Krakovna et al.
SEEDS + HOLDOUT↗

Test-set contamination

Proving that black-box models have memorized their evaluation sets. GOLD's answer: five fresh sealed seeds plus one frozen holdout the procedure never touched — a single lucky pass never counts.

arxiv.org/abs/2310.17623
GATE 04↗

Bootstrap confidence bounds

The win is a lower confidence bound on the mean paired difference — not a point estimate. If the interval touches zero, luck is still on the table, and the gate fails.

wikipedia.org/wiki/Bootstrapping
GATE 04↗

Bonferroni correction

Every extra slice tested multiplies the chance of a false win. α is divided across slices so "it won somewhere" can't quietly become "it won."

wikipedia.org/wiki/Bonferroni_correction
GATE 04↗

The multiple comparisons problem

The winner's curse: run enough comparisons and noise wins one of them. Leaderboards built on many unreported comparisons are mostly reporting their luck.

wikipedia.org/wiki/Multiple_comparisons_problem
GATE 01↗

Data dredging / p-hacking

Searching the data until something looks significant. The commit gate closes this structurally: procedures are fingerprinted before the sealed seed exists.

wikipedia.org/wiki/Data_dredging
ALL GATES↗

Statistical power

Too few samples can't distinguish skill from noise, however real the effect. GOLD fixes n=300 paired instances per slice before the run — sized, not improvised.

wikipedia.org/wiki/Statistical_power
SEEDS + HOLDOUT↗

Overfitting

Winning on the data you tuned against and losing on everything else. The frozen holdout exists solely to catch a procedure that learned the test instead of the task.

wikipedia.org/wiki/Overfitting
The algorithm, in one line: freeze before you look → give both sides the same fight → score against a sealed truth → demand the paired win survives bootstrap and correction → prove it isn't the prior, the proxy, or the compute budget → then repeat on seeds it has never seen.

How the loop runs

Stop only when the gate passes.

The standard is a loop, not a report. spec → plan → test → build → verify → review → commit — and verify has teeth.

1

Commit before you see the test

Both procedures are fingerprinted. The sealed seed is derived from the commit hash plus fresh entropy — drawn after the code is frozen. Tuning after the fact is structurally impossible.

2

Run the six gates on real outcomes

Every truth() score comes from an outcome that actually happened. Synthetic inputs, if any, are labeled. Mocked runs fail by definition — the placebo gate catches them.

3

Five fresh seeds, then the frozen holdout

GOLD must hold on five independent seeds — a single lucky pass never counts. Then one final run on a holdout set the procedure has never touched. All six, or the loop continues.

4

Commit with the receipt attached

The full report — wins, losses, flags, bounds, cost — ships with the commit. The receipt is the deliverable. "Trust me" is not a deliverable.
